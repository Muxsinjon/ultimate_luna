# LunaWindow: project rules

**LunaWindow** ("Explore. Compare. Plan. Experience.") is a web app for the NASA Space Apps 2026 challenge "Lunar Landing Site Navigator". It answers WHERE, WHEN and WHY: which site, which dates, and which Sun/Earth geometry explains the result. It lets **mission planners, educators and the public** compare lunar landing sites and dates in seconds. For any site and time it shows where the Sun and Earth sit relative to the **real terrain horizon** (LRO LOLA). From that it derives power windows, direct-to-Earth link windows, sunset and Earthset countdowns, and viable landing dates when a schedule slips. Deadline: Sun 2026-11-15, 23:59 local-event time.

It has four connected workspaces that share one mission state (`lib/state.ts`, mirrored in the URL):
- **Explore & Compare** (Site A vs Site B)
- **Mission Window Finder** (requirements, search, "Why this window?")
- **Surface View** (an observer's perspective)
- **About & methodology**

There is also a welcome screen, a guided demo and a mission summary export. **Planner** mode shows the numbers; **Explain** mode adds plain-language text.

## Physics rules (non-negotiable)
- **Two visibility models.** Always label the active one next to results (`MODEL_LABEL` in `lib/visibility.ts`).
  - `terrain` (default): visible while the **upper limb** is above the local LOLA terrain horizon (`site.horizon`).
  - `geometric`: visible while the disc **centre** is above 0°, with the label "Geometric visibility — local terrain obstruction not included." Partial discs are not resolved in this model.
- **Sampling.** Metrics use hourly samples on half-open intervals: a sample at t covers [t, t + 1 h). Durations are qualifying samples × 1 h. Rise and set times are shown as a one-hour window. **Never claim sub-hour timing.**
- **No data, no claim.** Times outside the supported range (2023–2031) are never extrapolated. Clamp them with an explanation (`clampToCoverage`), or mark the result as "insufficient data".
- Disc sizes:
  - The Sun's disc is 0.533° (radius `SUN_RADIUS_DEG` = 0.2666°).
  - Earth's disc is about 1.9°; its radius is computed from the live Earth–Moon distance: `asin(6371 / d)`.
  - Report partial visibility as the **% of disc area above the horizon**, using the circular-segment formula `discFractionAbove()`.
- In the terrain model, **sunrise and sunset happen when the upper limb crosses the terrain horizon** (`margin + radius = 0`). Earthrise and Earthset use the same rule.
- Distant terrain: horizon masks use **exact spherical 3D geometry** (`pipeline/horizon_mask.py`, `web/src/lib/terrain.ts`). To first order this equals the curvature drop `d²/2R` with R = 1737.4 km, and a unit test asserts the agreement (`curvatureDropKm`).
- No atmospheric refraction.
- **Longitude:**
  - Stored internally (data files, `Site.lon`) as **east-positive 0–360°**.
  - Normalize every input with `normalizeLon360()`.
  - Display as −180..180 with E/W labels (`formatLon()`).
- **Time:** stored as UTC (ISO 8601 strings, epoch ms in memory). The UI shows UTC by default, with a local-time toggle.
- The Earth position includes **libration**. It comes from JPL Horizons sub-observer points (MOON_ME frame), never from a fixed point.
- Every curated site needs a `source` citation. Unverified coordinates set `verify: true`, which shows a badge.

## Data contract (`web/public/data/`, generated by `pipeline/`)
- `ephem.json` + `ephem.bin`:
  - The `.bin` is Float32 LE with rows × 6: `[earth_x_km, earth_y_km, earth_z_km, sun_x, sun_y, sun_z]`, in the MOON_ME frame.
  - It ships every `shipStepH`-th hour (6 h, `shipCount` rows). `buildEphemeris()` upsamples it to hourly rows (`count`, `stepMs` = 1 h) with a uniform Catmull-Rom cubic (Sun re-normalized). Coverage ends at the last shipped row, 2031-12-31 18:00 UTC.
  - Measured vs Horizons topocentric az/el (9 sites × 38 in-coverage epochs, `pipeline/validate_astronomy.py`): Sun ≤ 0.0009°, Earth ≤ 0.0059°, Earth illuminated fraction ≤ 0.006 percentage points. Earth phase comes from `earthPhase()` (`lib/physics/earthPhase.ts`).
  - The full hourly file stays in `pipeline/out/` for the Python pipeline.
- `sites.json`:
  - Top level: `{ azStepDeg, maxDistanceKm, observerHeightM, terrain, sites: Site[] }`.
  - `Site = { id, name, group, lat (−90..90), lon (0..360 E), source, verify, elevationM, horizon: number[360/azStepDeg], horizonDistKm?: number[360/azStepDeg] }`. `horizonDistKm` is the distance of the terrain that sets the horizon at each azimuth; it drives "What blocks the Sun and Earth" (`lib/blockers.ts`).
  - `horizon[i]` is the terrain elevation angle (°) at azimuth `i·azStepDeg`, measured clockwise from north, for an observer `observerHeightM` above the surface.
- Browser terrain:
  - `dem_polar.json/.bin` is Int16 LE in metres above the 1737.4 km sphere. It uses a south polar stereographic grid `n×n`, `scaleM` per pixel, centre `offsetPx`, and covers lat ≤ `minLat`.
  - `dem_global.json/.bin` is Int16 LE, simple cylindrical, `ppd` pixels per degree, row 0 at 90° N, column 0 at 0° E.
- `pgda_sun.bin`, `pgda_earth.bin`: Uint8 on the polar grid. Values are % of time visible; 255 means no data.
- `terrain/<site>/illumination/` (Milestone 5): `illumination.json` plus `far_el.i16` (Int16 LE, 0.01°) and `far_d.u16` (Uint16 LE, 0.1 km), 21 × 21 × 720 far-field horizons outside the crop; `psr.u8` (401 × 401, 1 PSR / 0 / 255 no data, NASA PGDA product 90, static context). Browser algorithm: `lib/terrainShadow.ts`.
- `validation.json`: `{ period, worstElevationErrorDeg, sites[], illumination{}, missions[] }`.
- Mission Window Finder: `lib/finder.ts`. Candidate statuses are meets / partial (at most half of the active requirements fail) / fails / insufficient (outside data, or a required metric such as terrain unknown). Ranking: status, then fewer failures, then preference score (Σ w·n / Σ w; default weights = joint % only), then shorter darkness, then earlier start, then site id. The terrain requirement applies only to processed 5 m sites; unknown terrain is never a pass. Explanations are generated only from computed numbers (`checkSentence`).
- In-app time series: `Sample` in `web/src/lib/analysis.ts`. It has az/el, terrain horizon, margin and disc fraction for both the Sun and Earth, at the time `t` (ms UTC).

## Code conventions
- TypeScript strict. No `any` in physics code (`web/src/lib/physics/*`, `geometry.ts`, `analysis.ts`, `terrain.ts`).
- Physics lives in **pure functions**, separate from React components. Components never compute geometry inline.
- **Every physics function has a unit test** (`web/src/lib/**/*.test.ts`, Vitest).
- Styling uses only the design tokens in `web/src/styles/tokens.css`. No hard-coded colours in components, SVG or canvas; read them with `cssVar()`.
- User-facing text is in English and sentence case. Every number carries its unit.
- No NASA logos or insignia anywhere. Any AI-generated media needs a visible watermark.
- Log every AI-assisted task in `docs/AI_USAGE.md` (date, task, files).

## Definition of done (every change)
1. `npm run build` passes, with 0 TypeScript errors and 0 lint errors (`npm run lint`).
2. `npm test` (unit) and `python tests/e2e/smoke_test.py` (Playwright) pass.
3. There are no console errors or warnings on any screen.
4. Screenshots are taken (`tests/e2e/screenshots.py`) and checked against the design system.
5. `docs/AI_USAGE.md` is updated and the work is committed.
